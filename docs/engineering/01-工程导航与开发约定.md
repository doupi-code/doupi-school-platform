## 2. 后端模块与业务定位

后端运行基线由根Maven配置声明，启动入口在 `doupi-admin`。模块职责如下：

| 模块 | 职责 |
|---|---|
| `doupi-admin` | 应用启动、管理接口及Web层入口 |
| `doupi-framework` | 认证授权、安全过滤、数据源和缓存等框架配置 |
| `doupi-system` | 用户、角色、部门、岗位、菜单、字典、通知及系统配置 |
| `doupi-common` | 公共模型、工具、异常与通用约定 |
| `doupi-edu` | 教职工与班级档案、文印、物资领退、套装及喜报 |
| `doupi-stock` | 物资、供应商、出入库、盘点与库存报表 |
| `doupi-recruit` | 招生预约、教师绑定、校区、接待与小程序相关服务 |
| `doupi-cms` | 官网内容、页面搭建及公共内容接口 |
| `doupi-quartz`、`doupi-generator` | 定时任务、代码生成工具 |

以[模块声明](../../doupi-server/pom.xml)和各模块源码为准，不再将所有学校业务归入 `doupi-stock`。控制器分布在启动模块和部分业务模块中，查找接口时应搜索整个后端目录。

## 3. 本地开发与接口入口

管理后台和学校门户均在各自目录使用 `npm run dev` 启动；构建和静态检查命令为 `npm run build`、`npm run lint`。依赖安装方式以锁文件和工程要求为准。

| 项目 | 当前仓库开发配置 | 配置依据 |
|---|---|---|
| 后端 | 默认HTTP端口为 `8080`；启动前配置开发专用数据源、缓存及附件目录 | [application.yml](../../doupi-server/doupi-admin/src/main/resources/application.yml)、[资源配置目录](../../doupi-server/doupi-admin/src/main/resources) |
| 管理后台 | 开发端口 `5174`，基础路径 `/admin/`；`/api` 代理到本机后端并去掉该前缀；附件和调试相关路径也有代理 | [vite.config.ts](../../doupi-web-admin-react/vite.config.ts) |
| 学校门户 | 开发端口 `5173`；`/api` 代理到本机后端并保留原路径 | [vite.config.ts](../../doupi-web-client-react/vite.config.ts) |
| 微信小程序 | 请求封装使用 `/api/wx/dispatcher`，通过业务动作分派请求 | [cloudClient.js](../../doupi-miniApp/utils/cloudClient.js) |

管理后台请求基址由 `VITE_API_BASE_URL` 等配置控制，详见[请求封装](../../doupi-web-admin-react/src/api/request.ts)。开发代理不等于生产网关，不能将 `/api` 与 `/prod-api` 简单视为各端通用前缀。仓库当前默认代理本机后端，不应沿用旧文档中“启动前端即连接远程测试服务”的描述。

启动前检查有效配置，不直接沿用仓库中可能存在的历史连接信息。开发、测试与生产的连接、账号和存储范围应分别配置；不得为联调便利默认连接生产数据。

## 4. 管理后台与门户维护入口

- 管理后台页面在 `src/pages`，接口封装在 `src/api`。业务分为文印、教务档案与领退、库存、招生、CMS及系统管理等目录。
- 管理后台同时存在静态路由和后端菜单生成的动态路由，参见[动态路由处理](../../doupi-web-admin-react/src/store/usePermStore.tsx)及[菜单布局](../../doupi-web-admin-react/src/layouts/BasicLayout.tsx)。仅检查页面目录或菜单显示不足以确认授权范围，应同时核对接口权限与数据范围。
- 文印目前通过 `print` 路由进入，页面仍复用 `edu` 下的实现，参见[文印页面入口](../../doupi-web-admin-react/src/pages/print/record/index.tsx)。历史路径兼容不是新增业务模块。
- 官网内容读取入口见[CMS数据钩子](../../doupi-web-client-react/src/cms/hooks.ts)，页面视觉规范以现有样式和组件为依据。仓库记录的学校首页与作品集分发关系见[部署与数据维护](02-部署与数据维护.md)，不假定根路径始终属于学校门户。

## 5. 开发约定

1. **明确现状和计划。** 档案维护不能写成排课，登记扣库存不能写成审批完成，官网文章发布不能写成内部公文流转。功能说明需写清真实状态、可用动作、岗位责任和异常路径。
2. **使用真实业务数据。** 业务名单、库存、通知、待办与统计来自受控数据源。无数据展示空状态；加载失败展示失败与重试；示例或降级内容应明确标识，不得伪装成当前业务事实或成功结果。
3. **分离配置与业务。** 服务地址、接口基址、凭据由环境配置或部署配置提供。人数、价格、包装换算、审批规则等可变业务参数应有明确维护来源；固定枚举应与业务定义保持一致。
4. **保持库存事务一致。** 文印、出入库、领退、盘点涉及的单据及库存变更应处于一致的事务边界，异常时整体回滚。修改、作废、撤销、损耗和重试需要验证数量变化与关联单据，避免重复入账。
5. **区分鉴权与可见性。** 页面按钮和菜单只是交互入口；操作权限、数据范围及敏感字段访问还需要服务端约束。用户可同时具有多个岗位，应核对组合授权后的实际范围。
6. **保持响应与维护方式一致。** 沿用现有分页、统一响应、错误处理和模块接口约定。数据库关联字段的字符集与排序规则应一致，不使用查询补丁替代整体数据规范。
7. **验证真实闭环。** 依据改动验证正常、无权限、缺数据、重复提交、失败重试、库存不足及撤销等适用路径。构建通过只说明代码可构建，不代表业务流程或线上环境已验收。

## 6. 检查工具及适用范围

前端构建与静态检查见各自 `package.json`。后端构建和测试以Maven工程为准；发布脚本当前使用跳过测试的打包参数，发布成功不能作为测试通过的证据。

[项目文档检查器](../../scripts/check-project-docs.py)从仓库根目录运行：`python scripts/check-project-docs.py`。它只用Python标准库读取文档和SQL文件，核对本地链接、42模块进度主表、六节结构、接口表及同源DDL，不写文件、不连接数据库、不执行SQL。检查通过仅说明这些静态约束一致，不代替业务测试、迁移演练或验收。

结构事实与计划设计分别见[线上结构基线](../../database/baseline/production-2026-11-05.sql)、[完整目标结构](../../database/target/schema.sql)及[差异说明](05-数据库结构差异.md)；整理范围见[项目整理记录](06-项目整理记录.md)与[文件清理明细](07-文件清理明细.md)。

[防硬编码检查脚本](../../scripts/check-hardcoding.mjs)可从仓库根目录通过 `node scripts/check-hardcoding.mjs` 运行。它包含针对实体默认值、部分文印业务魔数、报表选项、移动端旧网关及部分前端地址写法的定向规则，不是完整的凭据扫描或业务数据真实性验收工具。

`scripts` 中还包含访问接口、执行SQL和修改数据的脚本。运行任何未熟悉的脚本前先阅读内容并确认目标环境，不能根据文件名将它们全部当作只读检查。
