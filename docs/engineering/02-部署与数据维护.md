# 部署与数据维护

更新：2026-11-06。本文汇总当前仓库中的发布入口、配置位置和数据维护约束。本轮整理了目录、脚本和配置，并只读复核正式库结构元数据；没有执行线上DDL/DML、导出业务记录或发起发布。作品集本地拆分及仓库配置整理不等于现网切换。执行维护前仍应核对实际环境、权限、版本及备份状态。

## 1. 发布入口与实际流程

| 工作流 | 触发与职责 | 服务器执行入口 |
|---|---|---|
| [deploy-server.yml](../../.github/workflows/deploy-server.yml) | `main` 上后端或相关发布文件变更时触发，也支持手动触发 | [deploy-server.sh](../../deploy-server.sh) |
| [deploy-admin.yml](../../.github/workflows/deploy-admin.yml) | `main` 上管理后台或相关发布文件变更时触发，也支持手动触发 | [deploy-admin.sh](../../deploy-admin.sh) |
| [deploy-client.yml](../../.github/workflows/deploy-client.yml) | `main` 上学校门户或相关发布文件变更时触发，也支持手动触发 | [deploy-client.sh](../../deploy-client.sh) |
| [deploy-all.yml](../../.github/workflows/deploy-all.yml) | 手动发起，按顺序发布后端、管理后台、学校门户 | 上述三个对应脚本 |

校园仓库发布范围仅后端、管理后台、学校门户三端。作品集已迁至同级独立项目`doupi-portfolio`，目前为无remote、无提交的本地main分支；专用工作流与脚本已从校园仓库移除，其后续发布独立维护。

当前工作流通过SSH触发服务器脚本，代码同步、依赖安装、构建和替换均在服务器执行。不是在GitHub Runner构建产物后再上传，也没有仓库工作流支持的 `main/test` 双分支自动发布规则。触发条件以各工作流的 `paths` 和分支配置为准。

工作流使用的连接凭据应由仓库Secrets和受控服务器配置管理，本文不保存账号凭据、密钥、公网地址或个人文件路径。

## 2. 后端与前端发布行为

### 后端

[后端发布脚本](../../deploy-server.sh)同步 `main`，在服务器执行Maven打包，备份现有JAR，再通过临时文件替换运行JAR并重启服务。备份保留策略、目标目录和服务名在脚本中配置。

当前健康检查逻辑为：重启后先等待8秒，再最多尝试10次，失败尝试之间等待2秒；检查后端 `/login` 的HTTP响应，接受 `200`、`401` 或 `404`。检查失败时尝试恢复最近备份JAR并重启。

上述检查只能作为服务HTTP响应的粗略信号，不能证明数据库可写、库存事务正确、权限有效或核心业务可办理。脚本未提供数据库变更回滚，也未在恢复后执行完整业务验收；发布打包当前跳过测试。

### 管理后台与学校门户

[管理后台脚本](../../deploy-admin.sh)和[学校门户脚本](../../deploy-client.sh)在服务器安装依赖、执行前端构建，将产物复制到临时目录，再切换静态目录并重载Nginx。

脚本在切换后删除旧静态目录，不能将其描述为具备与后端相同的失败自动回滚保障。前端发布前应另行确认产物留存和恢复方式，发布后检查页面入口、资源加载、路由刷新和接口访问。

`scripts/nginx-doupi.conf`本轮未改动：根路径仍指向外部作品集静态目录，学校门户仍通过`/index`等路径进入，后台仍使用`/admin`。作品集移出源码仓库不改变这些路径事实，也不表示已更新服务器文件。

有效网关规则决定各环境的路径、反向代理和附件映射。本地Vite代理与生产网关不是同一套规则，排障时应分别核对。服务状态与日志位置应从服务器生效的服务单元及启动参数确认，不直接将仓库样本作为现网事实。

## 4. 环境隔离与配置维护约束

开发、测试和生产应分别维护以下边界：

- 数据源与账号权限：测试账号仅有目标测试库所需权限，禁止默认使用生产管理账号联调。
- 缓存命名空间、分库与会话：确认会话、任务和业务缓存不会跨环境相互影响。
- 附件存储与对外映射：上传目录及网关路径对应正确环境，避免测试覆盖或暴露生产附件。
- 服务端口、部署目录和发布入口：切换目标前核对，避免测试构建覆盖生产产物。
- 配置与凭据：通过受控配置注入，文档、日志和示例中不保存真实凭据。

不同数据库、Redis逻辑分库和不同附件目录是隔离措施，不能据此宣称已经实现物理主机或网络隔离，也不能保证账号授权正确。隔离验收需要核对有效连接、访问权限和实际读写范围；本文未执行该验收。

各模块第4节与目标结构同步维护；完整分层说明代码保留在第5节，公共约定见[公共契约](../../development-plan/00-shared/公共契约.md)。旧开发计划生成器及分散结构目录不再作为当前建库或校验入口。没有“将所有SQL任意顺序全部执行”的标准安装步骤，本轮没有制作或执行正式库增量迁移。

维护前需确认当前库结构、已执行变更、适用版本和脚本幂等性。新唯一键和外键须另行核验历史重复、孤儿引用及身份/数量映射；只读结构采集不能证明业务数据已满足这些条件。初始化数据、演示数据和真实业务流水分别管理。

业务字符字段使用`utf8mb4`，关联列的类型、字符集和排序规则必须兼容；目标结构保留线上既有属性，新表默认`utf8mb4_unicode_ci`，明确要求区分大小写的字段保留专用规则。历史[字符集转换脚本](../../database/history/repair/convert_collation.sql)已归档，包含结构变更，不能因文件存在认定现网已统一转换，更不能直接套用到当前目标结构。

文印、出入库、领退和盘点维护不仅涉及单表，还影响库存、关联单据及统计口径。修改历史数据应先明确联动范围及复核方式，避免只改单据或只改库存。

## 6. 备份、恢复与危险操作

每次结构变更、历史数据修复或跨环境迁移前，应确认可恢复备份、适用时间点、附件关联、恢复负责人及恢复验证方式。备份成功信息不能代替恢复验证。

依赖Docker的旧备份模板已随废弃部署材料移除。后端发布脚本保留的JAR备份不等于数据库或附件备份；当前原生数据库和附件的备份、恢复步骤仍需维护者按有效环境确认。结构基线仅含DDL，不能用于恢复业务数据。

仓库存在[历史生产清理脚本](../../database/history/repair/clean_production_data.sql)等清空流水、重置库存的材料。它们会影响单据、审计记录或账号关联，属于特殊数据处置，不是日常重置、初始化或修复步骤。跨环境全量覆盖同样不是标准同步操作。

本说明不提供清库或覆盖数据的可复制命令。确需执行时，应先形成具体的数据范围、保留要求、备份与恢复方案，并核对目标环境；不要为修复页面统计或补充演示数据而清空真实业务记录。

## 7. 发布与维护后的验证

本轮整理记录见[项目整理记录](06-项目整理记录.md)及[文件清理明细](07-文件清理明细.md)。在仓库根目录运行`python scripts/check-project-docs.py`，可使用[文档检查器](../../scripts/check-project-docs.py)只读核对链接、进度、六节详案与SQL结构一致性；它仅使用Python标准库，不连接数据库或执行SQL，不代表线上或业务验收。

后续实际发布或数据维护后，按变更范围核对服务和日志、页面与资源、登录与授权、目标环境连接、附件读写、关联单据与库存、真实数据统计及适用异常路径，记录版本、变更范围、执行结果和待确认事项。

区分“脚本执行成功”“服务能够响应”“功能验证通过”和“现网完成验收”。没有对应证据时，应明确写待验证，不使用“全量完成”“绝对隔离”或“自动发布保证业务正常”等结论。
